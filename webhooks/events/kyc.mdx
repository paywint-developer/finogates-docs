## Events

| Event                     | Sent when                                         | Additional fields                                     |
|---------------------------|---------------------------------------------------|-------------------------------------------------------|
| `user_kyc.applied`        | The user submitted the identity check.            | `status`, `verified_fields`                           |
| `user_kyc.in_review`      | The check is under review.                        | `status`                                              |
| `user_kyc.approved`       | The check is approved.                            | None                                                  |
| `user_kyc.semi_approved`  | The check is moved to semi-approved.              | `status` (`semi_approved`), `previous_status`         |
| `user_kyc.rejected`       | The check is rejected.                            | `reject_reason`                                       |
| `user_kyc.reopened`       | The check is reopened for the user to redo.       | `reopen_reason`, `previous_status`, `reopen_count`    |
| `user_kyc.required`       | A payment needs the user to complete KYC first.   | `intent_id` or `payment_id`, `status` (`required`), `note` |
| `user_kyc.deleted`        | The verification record is deleted.               | `delete_reason`                                       |

## Example

```json
{
  "id": "1c2d3e4f-5a6b-4c7d-8e9f-0a1b2c3d4e5f",
  "type": "user_kyc.rejected",
  "event_type": "user_kyc.rejected",
  "created_at": "2026-10-13T11:04:52.118904+00:00",
  "data": {
    "kyc_record_id": "3e4f5a6b-7c8d-4e9f-a0b1-c2d3e4f5a6b7",
    "user_id": "b3a9b622-cc63-4d3c-aad6-2d8e29e6f9d4",
    "reject_reason": "Document is unreadable"
  }
}
```

## Data Fields

<ResponseField name="user_id" type="string">
  The user being verified.
</ResponseField>

<ResponseField name="kyc_record_id" type="string">
  The verification record. Status changes reported during verification send it as `check_id`. These are `applied`, `in_review`, and some `approved` and `rejected` events.
</ResponseField>

<ResponseField name="status" type="integer | string">
  Sent on `applied`, `in_review`, and on `approved` and `rejected` events reported by our provider. The values are `1` pending, `2` in review, `3` approved, `4` rejected and `5` semi-approved. The value is repeated in `status_code`. `semi_approved` and `required` send a string.
</ResponseField>

## Update events

A change sent to an **approved** KYC with [Update User KYC Record](/api-reference/verification/update-user-kyc-record) waits for our review. The record stays approved during this time. Once every item is decided, you get one event.

| Event | Sent when |
| --- | --- |
| `user_kyc.update_approved` | At least one item was approved and is now on the KYC. |
| `user_kyc.update_rejected` | Every item was rejected. Nothing changed. |

```json
{
  "id": "6a7b8c9d-0e1f-4a2b-8c3d-4e5f6a7b8c9d",
  "type": "user_kyc.update_approved",
  "event_type": "user_kyc.update_approved",
  "created_at": "2026-10-29T09:12:44.512031+00:00",
  "data": {
    "kyc_record_id": "8f9a0b1c-2d3e-4f5a-8b6c-7d8e9f0a1b2c",
    "user_id": "b3a9b622-cc63-4d3c-aad6-2d8e29e6f9d4",
    "update_id": "0d1e2f3a-4b5c-4d6e-8f7a-9b0c1d2e3f4a",
    "status": "approved",
    "items": [
      {"id": "c1", "kind": "document", "document_type": "proof_of_address", "status": "approved"},
      {"id": "c2", "kind": "field", "field": "address", "status": "rejected", "reason": "The address does not match the proof of address."}
    ]
  }
}
```

<ResponseField name="update_id" type="string">
  The update. It matches the `pending_update.id` from when you sent it.
</ResponseField>

<ResponseField name="status" type="string">
  `approved` (at least one item was approved) or `rejected`.
</ResponseField>

<ResponseField name="items" type="array">
  Each item has its own `status` (`approved` or `rejected`). A rejected item also has a `reason`. `kind` is `field`, `document` or `classification`.
</ResponseField>
